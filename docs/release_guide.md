# Сборка и выпуск

Первый стабильный выпуск публикуется после приёмки диагностики и восстановления, внешнего AWG-клиента и загрузки после reboot. Текущее состояние описано в [протоколе готовности](verification_status.md). Зелёный CI проверяет сборку и контейнеры панели; он не подтверждает работу WARP на VPS.

До завершения оставшейся клиентской приёмки опубликован [первый предварительный выпуск `v0.1.0-rc.1`](https://github.com/khorevaa/awg-vps-control/releases/tag/v0.1.0-rc.1). Он помечен GitHub prerelease и устанавливается только по точному тегу. Проверены публичные загрузки и штатное обновление из его архива. Наличие такого выпуска не закрывает условия стабильного `v0.1.0`; `latest` его не выбирает.

## GitHub Actions

| Workflow | Запуск | Результат |
| --- | --- | --- |
| `test.yml` | Push в `develop`, `main`, `codex/**`, pull request или вручную | Проверки исходников, Linux amd64 bundle, scratch images, установка и readiness контейнеров на чистом runner, архив и SHA-256 |
| `publish_ui_images.yml` | Вручную с точной версией или из release workflow | Повторные проверки, получение проверенного bundle из того же запуска, публикация Web/Control в GHCR |
| `release_manager.yml` | Push тега `v<version>` | Проверка тега и файла `version`, успешная публикация образов, GitHub Release с тем же архивом и SHA-256 |

Проверки включают `gofmt`, `go vet`, имеющиеся Go-тесты, синтаксис JavaScript/Bash, manifest, запуск бинарников внутри образов и readiness Web → Control → Adapter → WARP agent. На CI-runner не устанавливаются AWG и официальный WARP: WARP agent работает без принятой сетевой интеграции. Удаление контейнеров не останавливает агент.

Workflow actions закреплены полными commit SHA. Проверки имеют `contents: read`; публикация образов получает `packages: write`, создание выпуска — `contents: write`. Сведения о личных VPS, SSH и секреты панели не нужны и в GitHub Secrets не добавляются.

## Образы и артефакты

- `ghcr.io/khorevaa/awg-vps-web:v<version>` — Web.
- `ghcr.io/khorevaa/awg-vps-control:v<version>` — Control и Adapter с разными аргументами и правами.
- `awg_vps_control_linux_amd64.tar.gz` — проверенный bundle: менеджер, установщик, Linux-бинарники, Compose, WARP systemd units, `version`, `source_revision`, `manifest.sha256`.
- `awg_vps_control_linux_amd64.tar.gz.sha256` — checksum скачиваемого архива.

WARP работает на хосте; отдельного образа WARP нет. AWG-образ не собирается. Установщик строит локальные образы из бинарников bundle, поэтому установка панели не зависит от анонимного доступа к GHCR.

Перед публикацией версионной пары оба образа загружаются под промежуточными тегами с commit SHA. Затем проверяются версия бинарника, revision/source/component labels и идентичность уже существующих версионных образов. Чужое содержимое под тем же тегом не перезаписывается. Registry не предоставляет транзакцию для двух тегов: при сбое после первого push повторный запуск завершает согласованную пару. После первой публикации нужно проверить публичную видимость обоих packages и анонимное скачивание.

## Порядок первого выпуска

1. Закрыть обязательные сценарии [плана](development_plan.md), обновить протокол готовности и итоговый README. Реквизиты стенда и исходные диагностические снимки оставить локально.
2. Записать стабильную версию в `version`, например `0.1.0`; закоммитить изменения и получить зелёный `test.yml` для публикуемого commit.
3. Создать тег на этом commit и отправить его:

   ```bash
   git tag -a v0.1.0 -m 'Release 0.1.0'
   git push origin v0.1.0
   ```

4. Дождаться всех jobs `release_manager.yml`. Проверить Release, checksum архива, обе версии образов и анонимный доступ GHCR.
5. Скачать опубликованный bundle, сверить checksum и проверить установку/обновление управляющим скриптом из этого выпуска.

Тег обязан совпадать с `version`. Теги с суффиксом после дефиса публикуются как prerelease. Описание берётся из `docs/releases/<тег_с_подчёркиваниями>.md`, например `v0_1_0_rc_1.md`; при отсутствии файла GitHub генерирует release notes. В описании кандидата перечисляются незавершённые проверки. Существующий GitHub Release автоматически не заменяется: ошибка повторного создания требует проверки уже опубликованных артефактов. Финальные теги не переносятся на другой commit.

Локальная сборка: `bash scripts/build_release.sh <новый_каталог>` либо `scripts/build_release.ps1`. На рабочем дереве с изменениями `source_revision` получает суффикс `-dirty`; публикация образов допускает только чистый commit текущего запуска. Проверенные локально workflows можно дополнительно проверить `actionlint` перед push.
