# Установка и эксплуатация

Для ручного управления предусмотрен `awg_vps_control.sh`, а после установки — команда `sudo awg-vps-control`. Без аргументов в терминале открывается интерактивное меню. Именованные команды пригодны для скриптов: `status`, `doctor`, `discover`, `attach`, `policy`, `setup-warp`, `repair`, `reconnect-warp`, `restart-awg --confirm`, `logs`, `ui-access`, `rotate-ui-access`, `update-ui`, `rollback-ui`, `uninstall-ui`.

Меню использует ту же политику и проверки, что веб-панель. Перед ручным переключением режима перечитывается ревизия; при конфликте чужая настройка не перезаписывается. Создание пользователей не входит в первый выпуск. Ни меню, ни команды не устанавливают AWG.

Первый профиль: Ubuntu 24.04, amd64, systemd, уже установленные Docker/Compose и AmneziaWG. Проект не устанавливает Docker или AWG. Runtime проекта использует Go и Bash; Python на VPS не требуется. Web, Control и Docker Adapter работают в трёх контейнерах без сети и Linux capabilities. Доступ к Docker socket есть только у Adapter.

## Сборка и установка панели

На машине разработчика требуется Go 1.26.9. В корне репозитория:

```bash
bash scripts/build_release.sh
tar -C .local -czf awg_vps_control.tar.gz release
scp awg_vps_control.tar.gz root@YOUR_VPS:/root/
```

Для Windows:

```powershell
.\scripts\build_release.ps1 -Go 'E:\gosdk\go1.26.9\bin\go.exe'
tar.exe -czf .local\awg_vps_control.tar.gz -C .local release
```

На VPS распакуйте архив в отдельный каталог и установите панель:

```bash
mkdir -p /root/awg_vps_release
tar -xzf /root/awg_vps_control.tar.gz -C /root/awg_vps_release
bash /root/awg_vps_release/release/install.sh /root/awg_vps_release/release
awg-vps-control healthcheck
awg-vps-control ui-access root@YOUR_VPS
```

Установщик проверяет полный manifest и SHA-256, собирает два scratch image из готовых Go binaries и сохраняет версионный каталог. Образ Control используется также отдельным контейнером Adapter с командой `adapter serve`. Контейнеры запускаются Compose с ожиданием readiness; после reboot их поднимает Docker через `restart: unless-stopped`. Go, npm и компилятор на VPS не нужны. До явного подключения и выбора политики VPN-файлы и маршруты не меняются. Access secret создаётся один раз; повторная установка сохраняет его.

На хосте остаются только проектные службы `awg_vps_warp.service` (WARP IPC и supervisor в одном Go-процессе) и `awg_vps_guard.service` (ранняя защита выхода). Собственная служба Cloudflare `warp-svc.service` появляется при отдельной установке WARP. Общего host bridge и systemd-службы для UI нет. Runtime-каталоги sockets создаёт `/etc/tmpfiles.d/awg_vps_control.conf`.

Adapter работает как UID 10003 с дополнительной фактической группой Docker socket. Установщик записывает её числовой GID в `AWG_DOCKER_GID` файла `/etc/awg_vps_control/ui.env`. Docker API даёт Adapter полномочия уровня root: read-only mount socket этого не ограничивает. Поэтому это отдельный доверенный компонент; Web и Control не получают socket, произвольный shell или доступ к Docker API. Метрики хоста передаются отдельными read-only файлами, без монтирования корня хоста. Показатель диска относится к разделу с данными панели.

`ui-access` выводит команду SSH-туннеля, уникальный адрес вида `http://awg-….localhost:8787` и секрет входа. Выполните SSH-команду на своём компьютере, откройте именно выданный адрес и введите секрет. Панель не слушает публичный TCP-порт. SSH-пользователь должен иметь доступ к root-only Unix socket через разрешённую сервером модель доступа. В первом профиле используется root SSH.

## Подключение существующего AWG

В разделе «Подключение сервера» выберите обнаруженный контейнер, Docker-сеть и существующий DNS-контейнер, если он используется. При нескольких сетях выбирается сеть, общая для AWG и DNS. Attach сохраняет идентификаторы и исходную ревизию, не изменяя родные файлы Amnezia.

После подключения доступны обзор, список peers, маскированная конфигурация, диагностика и журналы. До первого явного сохранения режима панель показывает «Выберите режим выхода»: отсутствие WARP не считается согласием изменить маршруты.

## WARP и прямой выход

Для управляемой интеграции нужны `ip`, `nft`, `iptables-nft`, `ip6tables-nft`, `nsenter`, `curl` и `conntrack`. На Ubuntu недостающий conntrack устанавливается отдельно:

```bash
apt-get update
apt-get install --no-install-recommends conntrack
```

При первой настройке сохраните режим без WARP, затем запустите установку WARP, после её завершения включите WARP в политике. Кнопка настройки устанавливает официальный клиент и готовит защищённый путь. Она не включает WARP вместо пользователя. Существующая регистрация и настройки не сбрасываются молча.

| Выбор | Поведение |
| --- | --- |
| WARP явно выключен | Прямой выход |
| WARP включён, исправен | Выход через WARP |
| WARP неисправен, разрешение прямого выхода снято | Выход клиентов блокируется |
| WARP неисправен, разрешение установлено | Автоматический прямой выход |
| WARP восстановился | Немедленный возврат всего трафика в WARP |

Галочка разрешения прямого выхода никогда не включается автоматически. Снятие разрешения прекращает прямой выход и существующие соединения. Переключения могут прерывать загрузки и звонки. Автовосстановление меняет только собственные сетевые объекты и WARP; Docker/VPS/AWG автоматически не перезапускаются.

Сетевой адаптер использует отдельный veth для расшифрованного клиентского трафика и независимую nftables-защиту. Неизвестные топологии, пересечения ресурсов и маршрутизируемый IPv6 на клиентском AWG-интерфейсе приводят к отказу от изменения. Link-local IPv6 допустим, но клиентский IPv6 блокируется отдельно; IPv6 хоста не отключается. Подробности и ограничения — в [host runtime](host_runtime.md).

## Обновление, восстановление и удаление UI

```bash
awg-vps-control update-ui /root/new_release
awg-vps-control rollback-ui
awg-vps-control rotate-ui-access
awg-vps-control uninstall-ui
```

Обновление проверяет новую сборку и readiness цепочки Web → Control → Adapter → WARP, включая доступ к Docker. При ошибке пытается вернуть предыдущую сборку; сообщение об успешном восстановлении выдаётся только после проверки. Откат приложения не откатывает сетевую политику или состояние WARP. При переходе со старой упаковки установщик отдельно отключает прежние UI/host/supervisor units, сохраняя state и guard; контейнеры новой схемы обслуживаются только Compose.

`uninstall-ui` удаляет три контейнера панели: Web, Control и Adapter. Хостовая WARP-служба с supervisor, boot guard, состояние и защитные правила сохраняются, чтобы выбранная политика продолжала работать. Это не полное снятие сетевой интеграции. Автоматическое удаление WARP, Docker и AWG не предусмотрено.

При `manual_recovery_required` проверьте журнал операции и `awg-vps-control doctor`; неопределённая операция не повторяется после перезапуска автоматически. Не удаляйте guard вручную при строгой политике. Запуск Docker/WARP после перезагрузки зависит от успешной ранней установки защиты после принятия интеграции под управление.

## Восстановление административного доступа

В текущей dev-сборке обнаружен блокирующий дефект: включение WARP может сделать SSH недоступным. Если это произошло, из root-консоли провайдера остановите WARP и его автоматическое восстановление:

```bash
systemctl stop awg_vps_warp.service warp-svc.service
```

Команда не останавливает AWG и Docker, не разрешает прямой выход клиентов и не меняет сохранённую галочку. При строгой политике клиентский выход может оставаться заблокированным. Не останавливайте `awg_vps_guard.service`: после интеграции Docker зависит от него. До исправления не запускайте WARP agent повторно и не перезагружайте VPS — сохранённая политика может снова подключить WARP. Сохраните снимок правил и журналов локально для диагностики.

## Проверки разработчика

```bash
(cd ui/web && go vet ./... && go test ./...)
(cd ui/control && go vet ./... && go test ./...)
node --check ui/web/app/static/app.js
```

HTTP-сценарии находятся в `ui/web/tests/web.http`; приватные параметры задаются локально. Новые Go-тесты не добавлены согласно правилам проекта. Проверки охватывают Go, JavaScript, shell, Compose и systemd units, Linux binaries и Docker images. Проверка HTTP-статусов не заменяет сетевые испытания fail-closed, DNS, переподключения и восстановления.

Не включайте действующие конфигурации, секреты, сведения о личных VPS и сырые диагностические снимки в коммиты, CI и публичные отчёты. Локальные материалы испытаний находятся в игнорируемом `.local/`.
