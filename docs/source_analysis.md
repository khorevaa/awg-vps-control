# Анализ источников

Дата анализа: 12 ноября 2026 года. Этот документ отделяет подтверждённое устройство источников от решений для нового проекта. На этапе анализа источников VPS не проверялся; последующие интеграционные испытания описываются отдельно, без публикации сведений о тестовом окружении.

Дополнение по будущей установке/обновлению AWG: в официальном [amnezia-vpn/amnezia-client](https://github.com/amnezia-vpn/amnezia-client/tree/dev/client/server_scripts/awg) находится набор `Dockerfile`, `run_container.sh`, `configure_container.sh`, `start.sh` и шаблонов, используемых клиентом Amnezia. Это не подтверждённый самостоятельный универсальный установщик. [Dockerfile](https://github.com/amnezia-vpn/amnezia-client/blob/dev/client/server_scripts/awg/Dockerfile) использует базовый образ `amneziavpn/amneziawg-go`; [run_container.sh](https://github.com/amnezia-vpn/amnezia-client/blob/dev/client/server_scripts/awg/run_container.sh) требует подготовленных переменных и DNS-сети. [configure_container.sh](https://github.com/amnezia-vpn/amnezia-client/blob/dev/client/server_scripts/awg/configure_container.sh) генерирует новые ключи и перезаписывает `awg0.conf`; повторять его над существующей установкой для обновления нельзя. Перед реализацией этапа 9 требуется подтвердить полный официальный контракт и закрепить конкретный release/commit. Сторонний установщик вместо официального источника не выбран.

Для перенесённого в текущую работу `install-awg` выбран стабильный [release 5.1.0.6](https://github.com/amnezia-vpn/amnezia-client/releases/tag/5.1.0.6), commit `ac175c8a8147cfe56f98c8372ec17ea2ba00bb02`. Контракт включает общие `prepare_host.sh` / `build_container.sh`, AWG run/configure/start и AmneziaDNS. Глобальный `setup_host_firewall.sh` исключён: wrapper проверяет нужные предпосылки и не выполняет общий тюнинг хоста. Официальный AWG 3.1 profile поддерживается уже AmneziaVPN `5.0.3.0`: [генератор](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/core/installers/awgInstaller.cpp) использует те же поля, а клиентский template совпадает с `5.1.0.6`. Это подтверждает формат, но не заменяет внешнего клиентского испытания.

Предложенный пользователем [bivlked/amneziawg-installer](https://github.com/bivlked/amneziawg-installer) изучен отдельно. По его README установка использует модуль ядра и `awg-quick@awg0` на хосте, конфиг `/etc/amnezia/amneziawg/awg0.conf`, профили `/root/awg`; это не Docker-установка Amnezia с общим `clientsTable`. После уточнения пользователь сохранил Docker и официальные скрипты Amnezia. Этот сторонний проект не запускается на стенде и не становится источником обновлений нашего менеджера.

## 2. Что действительно используется в ocserv-vps

### Стек

- Два независимых модуля `ui/web` и `ui/control`, `go 1.26`, без внешних Go-зависимостей. Сборка и CI закреплены на Go 1.26.5.
- Web использует стандартный HTTP-сервер Go. HTML, CSS и vanilla JavaScript встроены через `go:embed`; нет npm-сборки или frontend-фреймворка.
- Хостовые операции: Bash, systemd, Docker Compose v2. Python применяется в отдельных утилитах и существующих проверках. Node 22 в CI нужен для проверки синтаксиса JavaScript.
- Хранилище сессий и аудита — защищённый JSON-файл; внешней СУБД нет.

Источники: [web/go.mod](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/ui/web/go.mod), [control/go.mod](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/ui/control/go.mod), [CI](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/.github/workflows/test.yml).

### Разделение полномочий

Web и Control работают в отдельных контейнерах с `network_mode: none`, без Docker socket. Браузер подключается через SSH forwarding к Unix `web.sock`. Web обращается к Control через Unix `control.sock` и протокол JSON lines; Control проверяет UID через `SO_PEERCRED`.

Web работает от UID 10001. Исходный Control работает от root с ограниченными capabilities, включая `DAC_OVERRIDE`; его нельзя считать полностью непривилегированным. Для AWG требуется пересмотреть необходимые права, поскольку управление network namespace отличается от работы с `occtl`.

Фиксированные systemd-мосты выполняют перезапуск контейнера, снимок журналов и обслуживание сертификата. Это не универсальный интерфейс запуска shell-команд.

Источники: [install-ui.sh](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/scripts/install-ui.sh), [control/server.go](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/ui/control/server.go), [scripts/common.sh](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/scripts/common.sh).

### Доступ и хранение

Секрет обменивается POST-запросом на серверную сессию. Используются cookie `Secure`/`HttpOnly`/`SameSite=Strict`, проверка Host и Origin, CSRF-токен, строгий JSON, ограничения размера запросов. Секрет не передаётся в URL. Сессионные токены хранятся в виде хешей; чувствительные ответы имеют `no-store`.

State-файл имеет ограниченные права и записывается атомарно. Отдельные действия раскрытия секретов попадают в аудит. В исходной реализации ошибка записи аудита логируется, но не обязательно отменяет операцию.

Источники: [web/server.go](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/ui/web/server.go), [web/store.go](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/ui/web/store.go).

### Интерфейс

Русский интерфейс с sidebar, карточками, таблицами, поиском, пагинацией, модальными окнами и уведомлениями. Есть светлая, тёмная и системная темы. Конфигурация сначала открывается для чтения; редактирование включается отдельным действием. Credentials показываются после создания или смены пароля.

Сохраняем эти принципы и CSS tokens, заменяя предметную область ocserv на AWG peers, handshake, трафик и маршруты. Источники: [index.html](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/ui/web/app/static/index.html), [styles.css](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/ui/web/app/static/styles.css).

### Ограничения повторного использования

1. Установщик исходной панели меняет конфигурацию VPN и Compose и может перезапускать ocserv. Его нельзя переносить целиком в режим подключения к существующему AWG.
2. Запись конфигурации проверяет SHA-256, использует lock, candidate, проверку `ocserv --test-config`, fsync и rename. Откат реализован при ошибке записи/создания триггера. После успешного триггера нет полного цикла проверки фактического restart и восстановления runtime при его провале. README описывает более сильную гарантию, чем этот код.
3. Пароли и пользовательские сессии ocserv не соответствуют peers и ключам AWG. Аналог «отключить сессию» требует нового смысла.
4. TLS-сертификаты и HTTP-маскировка ocserv не переносятся в AWG как обязательные функции.

Источник для транзакции конфигурации: [control/configuration.go](https://github.com/khorevaa/ocserv-vps/blob/e05a4f9a3e11a6a5e7883b459ad921ac7bacc8e8/ui/control/configuration.go).

## 3. Что было сделано в предыдущем чате

По итоговой истории разработана схема для Ubuntu 24.04 с уже работающим AWG в Docker, DNS-контейнером и официальным WARP на хосте. В итоговом варианте используется полный WARP-туннель, а не SOCKS-прокси и не Mihomo. Ниже описан исторический результат с обязательным WARP и блокировкой прямого выхода при его отказе. Согласованная политика нового продукта приведена в разделе 6 и допускает иной режим только по явному выбору владельца.

Основные артефакты:

| Файл | Назначение |
| --- | --- |
| `awg_warp.conf` | Настройки топологии и восстановления |
| `awg_warp_config.sh` | Валидация настроек, обнаружение и сохранение топологии |
| `restore_awg_warp.sh` | Подготовка правил, применение, проверка и supervisor |
| `awg_warp_restore.service` | systemd `Type=notify`, watchdog, автоперезапуск |
| `restore_awg_direct.sh` | Явный возврат к прямому выходу |
| `warp_ssh_route.sh` | Сохранение маршрута административного SSH |
| `update_awg_warp.sh`, `baseline.sha256` | Обновление вспомогательных файлов с проверкой исходного состояния и восстановлением |

Для исследованной установки использовались контейнер `amnezia-awg2`, интерфейс `awg0`, конфигурация `/opt/amnezia/awg/awg0.conf`, DNS-контейнер `amnezia-dns` и явно выбранные Docker-сети. Эти имена — обнаруженные значения конкретной установки, а не обязательные константы будущего продукта.

Ключевые свойства итоговой схемы:

- Адрес VPN-клиента сохраняется до хоста: дополнительное правило в контейнере стоит перед его MASQUERADE.
- Policy routing направляет клиентский и DNS-трафик через WARP. Внешний транспорт AWG и доступ SSH обрабатываются отдельно.
- Собственные firewall-цепочки и `unreachable default` блокируют прямой выход клиентов при отказе WARP. Значимы не только наличие правил, но и порядок переходов `FORWARD`/`DOCKER-USER` и NAT.
- Supervisor замечает изменение интерфейса WARP, PID контейнера и правил, восстанавливает маршруты, ограничивает повторные подключения и перезапуски.
- После восстановления выполняются HTTPS-проверка с `warp=on|plus` и UDP DNS из сетевого пространства контейнера с адресом клиентской подсети.
- Отдельный сбой DNS не считается достаточной причиной перезапускать исправный WARP.
- Обновление проверяет baseline checksum и защищает ручные правки от молчаливой перезаписи.

Границы подтверждённого результата:

- Локальные артефакты и отчёт чата не заменяют новую проверку VPS.
- Представленные правила и probes в основном IPv4. Нельзя автоматически заявлять полную защиту IPv6 от утечек.
- Внешние HTTPS/DNS probes в supervisor выполняются после применения/восстановления; это не непрерывный мониторинг всей передачи данных.
- Проба из namespace полезна для проверки выхода, но не доказывает работу реального клиента через внешний AWG handshake. Для приёмки потребуется отдельное клиентское подключение.
- Эти скрипты требуют адаптации прав, блокировок, владения ресурсами и статусов операций перед вызовом из панели.
- Защита при пропадании WARP-интерфейса не означает защиты от любых повреждений правил. Если исчезает правило сохранения client source, трафик может получить адрес контейнера и обойти source-based policy до реакции supervisor. Это отдельный риск, который необходимо устранить до приёмки режима обязательного WARP.
- В SSH-helper найдено широкое исключение по адресу административного клиента. При переносе его нужно ограничить административным трафиком, чтобы оно не разрешало обход WARP клиентам VPN.
- Updater атомарно заменяет отдельные файлы и хранит предыдущую версию, но не выполняет единую атомарную транзакцию всех сетевых правил. Восстановление после прерывания требует дополнительного проектирования.
- Unit ссылается на `warp_ssh_route.service`, которого нет в итоговом локальном bundle. Зависимость и восстановление после reboot должны быть проверены отдельно; в итоговой проверке прошлого чата reboot не выполнялся.
- Управление peers и метаданными Amnezia в прошлом чате не разрабатывалось.

## 4. Уточнения по AWG

Официальная документация описывает несколько поколений AWG и разные наборы параметров. Поэтому совместимость нужно определять по установленному runtime, tools и клиентам, а не по одному имени контейнера. Первый целевой профиль — существующая Docker-установка Amnezia с подтверждёнными возможностями runtime; неизвестные параметры должны сохраняться, а неподдерживаемое редактирование блокироваться. [Документация AmneziaWG](https://docs.amnezia.org/documentation/amnezia-wg/).

Имя `amnezia-awg2` само по себе не доказывает версию протокола: в исследованной ревизии официального клиента enum `Awg2` соответствует этому имени, но после переустановки тому же типу назначается `protocolVersion = awgV3`. Это факт исходников, а не проверка установленной версии на VPS. [Соответствие имени](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/utils/containers/containerUtils.cpp#L24), [версия после переустановки](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/controllers/selfhosted/installController.cpp#L341).

`awg show ... dump` может содержать private key интерфейса и preshared keys peers. Сырые результаты нельзя передавать в Web, диагностику или аудит. [Официальный формат вывода](https://github.com/amnezia-vpn/amneziawg-tools/blob/master/src/man/wg.8).

`awg-quick` обрабатывает исполняемые `PreUp`/`PostUp`/`PreDown`/`PostDown`, а `SaveConfig` способен перезаписывать persistent-конфигурацию. Это требует отдельной политики редактирования и согласования writers; механическое копирование редактора `ocserv.conf` небезопасно. [Исходный код awg-quick](https://github.com/amnezia-vpn/amneziawg-tools/blob/master/src/wg-quick/linux.bash).

## 5. Штатное управление клиентами Amnezia

Следующие факты относятся к указанному snapshot `amnezia-client`; полная совместимость с другими версиями и фактической установкой пока не проверена.

### Файлы и операции

Для исследованного современного AWG используются `/opt/amnezia/awg/awg0.conf` и `/opt/amnezia/awg/clientsTable` внутри контейнера. Конфиг хранит peer public key, PSK и AllowedIPs. `clientsTable` — JSON-массив записей с `clientId`, равным публичному ключу, и `userData` с `clientName` и `creationDate`. При обнаружении ранее существовавшего peer дата может отсутствовать. [Пути](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/utils/constants/protocolConstants.h#L277), [создание записи](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/controllers/selfhosted/usersController.cpp#L448).

| Операция | Порядок в исследованном клиенте |
| --- | --- |
| Просмотр | Чтение `clientsTable`, дополнение состояния данными runtime из `wgShow`; восстановление списка по конфигу выполняется при пустой таблице |
| Создание | Генерация ключей в приложении, выбор IP, добавление `[Peer]` в конфиг, `awg syncconf awg0 <(awg-quick strip …)`, затем добавление имени и даты в `clientsTable` |
| Переименование | Изменение `userData.clientName` и запись `clientsTable`; конфиг и runtime не меняются |
| Отзыв | Чтение конфига, удаление секции peer, запись конфига, удаление записи из `clientsTable`, затем `syncconf` |

Источники: [создание peer и применение](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/configurators/wireguardConfigurator.cpp#L182), [добавление metadata после createConfig](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/controllers/selfhosted/exportController.cpp#L78), [просмотр](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/controllers/selfhosted/usersController.cpp#L340), [переименование](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/controllers/selfhosted/usersController.cpp#L507), [отзыв](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/controllers/selfhosted/usersController.cpp#L597).

В памяти `clientsTable` дополняется handshake, счётчиками трафика и AllowedIPs. Сам refresh не сохраняет это дополнение, однако последующие операции сериализуют всю таблицу. Поэтому такие поля могут присутствовать и в файле. Панель должна читать существующие записи и сохранять неизвестные и неизменяемые поля, а актуальную статистику брать из runtime. Неизвестная структура или параметр не дают права молча переписать запись по собственному шаблону.

### Ключи и отключение клиента

Клиентский private key генерируется в приложении и входит в выдаваемый профиль; в исследованном пути он не записывается в серверный peer-конфиг или `clientsTable`. PSK хранится на сервере в `wireguard_psk.key` и в секциях peers. Поэтому по двум штатным серверным файлам нельзя восстановить полноценный профиль существующего клиента. Согласованная функция панели — однократная выдача профиля при создании без собственного постоянного хранилища client private keys. Повторная выдача того же профиля без исходного private key не обещается. [Генерация ключей](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/configurators/wireguardConfigurator.cpp#L49), [чтение PSK и запись peer](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/configurators/wireguardConfigurator.cpp#L164).

В изученном контракте есть просмотр, создание, переименование и отзыв; штатного постоянного `disabled`/`enabled` состояния нет. Удаление только из runtime временно: следующий `syncconf` или запуск из файла может вернуть peer. В согласованный объём панели не входят собственные поля блокировки или дополнительные записи для хранения отключённых пользователей. [UsersController](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/controllers/selfhosted/usersController.h#L43), [запуск из конфига](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/server_scripts/awg/start.sh).

### Граница совместного управления

В исследованной цепочке записи не обнаружены общий межпроцессный lock, сверка ревизии перед заменой или транзакция со сторонним менеджером. Helper использует `docker cp` для замены и `cat … >> …` для добавления. Несколько шагов между конфигом, metadata и runtime могут завершиться частично. Собственная блокировка панели не блокирует штатный клиент Amnezia. [Helper записи](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/utils/selfhosted/sshSession.cpp#L117).

Согласовано последовательное совместное управление: обе программы читают и изменяют те же штатные файлы внутри контейнера; отдельной базы пользователей панели нет. Перед операцией панель заново читает состояние, проверяет доступные ревизии и после применения сверяет файл и runtime. Это помогает обнаруживать конфликты и частичное выполнение, но не гарантирует безопасную одновременную запись с Amnezia. Параллельное редактирование двумя программами не является поддерживаемым режимом.

Серверная перенастройка Amnezia может заново создать ключи и конфиг либо пересоздать контейнер. Панель должна обнаруживать смену установки и проверять привязку; она не должна автоматически восстанавливать прежних peers поверх новой конфигурации. [Перенастройка](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/core/controllers/selfhosted/installController.cpp#L277), [генерация AWG-конфига](https://github.com/amnezia-vpn/amnezia-client/blob/864c1faab81166579a43a06fde9dbc9076b0be92/client/server_scripts/awg/configure_container.sh).

## 6. Согласованные решения для нового проекта

Эти решения получены после обсуждения требований. Они задают новое поведение продукта и не являются утверждением, что исторические скрипты уже его реализуют.

- Проект предназначен для личных VPS; на каждом сервере работает отдельная панель. Сохраняются стек, визуальный язык, Unix sockets и разделение полномочий `ocserv-vps`.
- AWG подключается как существующая установка. Проект не устанавливает и не обновляет AWG; автоматическое восстановление не перезапускает его. Перезапуск AWG доступен только как ручная операция.
- WARP необязателен. Панель может подключить существующий WARP или установить его отдельным явным действием владельца. Установка панели и обнаружение AWG сами по себе WARP не устанавливают.
- При использовании WARP автоматический прямой выход разрешается исключительно общей галочкой `Разрешить выход без WARP`. По умолчанию она выключена (`false`); сама панель её не включает. При снятой галочке отказ WARP должен блокировать прямой выход клиентского трафика; исторические ограничения защиты из раздела 3 остаются задачами реализации.
- При включённой настройке и отказе WARP разрешён автоматический переход на прямой выход для всего клиентского трафика, включая DNS. После проверки исправности WARP весь этот трафик автоматически возвращается в WARP. Обрыв существующих соединений при переключении допустим; сохранение их прежнего выхода не требуется.
- Снятие галочки при включённом использовании WARP сразу блокирует и существующие прямые соединения. Явно выбранная работа без WARP использует обычный прямой выход; отсутствие или отказ ранее включённого WARP таким выбором не являются.
- Автоматическое восстановление ограничено собственными правилами и маршрутами панели и обслуживанием WARP. Чужие сетевые правила не присваиваются панели; AWG автоматически не перезапускается. Причина, результат и время восстановления должны быть видны в диагностике.
- Первый выпуск посвящён обнаружению установки, диагностике и восстановлению работы AWG/WARP и маршрутов. Управление пользователями переносится в следующий этап: штатные просмотр, создание, переименование и отзыв через существующие файлы Amnezia, без дополнительной базы пользователей и состояния `disabled`. Новый клиентский профиль выдаётся один раз.

Из прошлого чата переносим принципы маршрутизации и восстановления, предварительно обезличив и адаптировав артефакты. Mihomo остаётся историческим источником. Необходимо разработать явные состояния WARP/direct/blocked, проверку фактического выхода и возврата, ограниченные host actions, восстановление после частичного выполнения и диагностическую модель с временем последней успешной проверки. Установка WARP и разрешение direct fallback — разные действия: установка WARP не включает fallback.
